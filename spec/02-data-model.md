# 02 — Модель данных

## Слой 1: каталог (статика из репозитория)

### Product — продукт

```ts
export interface Product {
	/** Стабильный слаг. Задаётся один раз и НИКОГДА не меняется и не переиспользуется. */
	id: string;
	/** Отображаемое название строчными: «томатная паста» */
	name: string;
	/** Отдел магазина — определяет группу в списке покупок */
	category: CategoryId;
	/** Единица состава. Без неё продукт учитывается только штуками */
	unit?: Unit;
	/** Уточнение, которое видно в списке: «маленькая», «именно ролтон» */
	note?: string;
	/** Имя файла в public/products/. Есть только у готового */
	photo?: string;
	/** Показывается в блоке «Часто» на экране плана */
	frequent?: boolean;
	archived?: boolean;
}
```

Каталог продуктов — `src/entities/product/lib/catalog.ts:3`. Объявлен через
`as const satisfies readonly Product[]`, поэтому `ProductId` выводится из самого массива, и состав блюда,
сославшийся на несуществующий продукт, не собирается.

### Dish — блюдо

```ts
export interface Dish {
	id: string;
	name: string;
	photo?: string;
	tags: Tag[];
	/** Сколько порций выходит из одной готовки */
	servings: number;
	ingredients: Ingredient[];
	/** Рецепт. Есть не у всякого блюда, добавляется коммитом */
	steps?: string[];
	archived?: boolean;
}

export interface Ingredient {
	product: ProductId;
	/** В единицах продукта. Отсутствует у специй: «лавровый лист» без граммовки */
	amount?: number;
}
```

Каталог блюд — `src/entities/dish/lib/catalog.ts:3`.

### Почему готовое — это продукт, а не третья сущность

В knowledge-base «готовое» было отдельным типом рядом с блюдами и продуктами. Для списка покупок чебурек ничем
не отличается от хлеба: обе строки — «купить N штук». Осталось два слоя: блюдо готовится и имеет состав,
продукт покупается как есть. Готовое стало отделом `ready`, а фотография — необязательным полем продукта.

Отсюда правило отрисовки на экране плана: **продукт с фотографией показывается карточкой, без — чипсом**.
Правило одно, а выглядит как три секции из knowledge-base — потому что у готового фото есть, а у моркови нет.

## Слой 2: личные данные (IndexedDB)

```ts
export interface PlanItem {
	/** `${kind}:${refId}` — одна позиция плана на одно блюдо или продукт */
	id: string;
	kind: "dish" | "product";
	/** id из каталога либо id своего продукта */
	refId: string;
	/** Целое ≥ 1. У блюда — сколько раз готовим, у продукта — сколько берём */
	qty: number;
	addedAt: number;
}

export interface Check {
	/** id продукта в списке покупок */
	key: string;
	checkedAt: number;
}

export interface CustomProduct {
	id: string;
	name: string;
	category: CategoryId;
	unit?: Unit;
	note?: string;
	createdAt: number;
	updatedAt: number;
}
```

## Схема Dexie

```ts
export const db = new Dexie("pantry") as AppDatabase;

db.version(1).stores({
	plan: "id, kind, refId, addedAt",
	checks: "key",
	customProducts: "id, createdAt",
});
```

**Почему пересечение типов, а не подкласс Dexie.** Привычная запись `class AppDatabase extends Dexie { plan!:
Table<PlanItem, string> }` ломается молча: при `useDefineForClassFields` объявление поля в подклассе
выполняется **после** конструктора Dexie и затирает уже присвоенную таблицу на `undefined`. Сборка и типы при
этом в порядке — падает рантайм на первом же запросе. Объявление таблиц типом убирает эту возможность целиком.

Индексы:

- `refId` в `plan` — удаление позиций при удалении своего продукта;
- `kind` — разделение блюд и продуктов;
- `addedAt` — порядок позиций;
- `createdAt` в `customProducts` — порядок в списке своих продуктов, чтобы строка не переезжала.

**Правило миграций.** Схема меняется только через `db.version(N).stores({...})`. Существующие версии не
редактируются никогда.

## Инварианты

**1. План хранит ссылку, а не снапшот.**
В `calories_count` запись дневника копирует калорийность, потому что правка каталога не имеет права переписать
историю задним числом. У плана истории нет: он живёт до конца текущей закупки. Наоборот, обновление каталога
должно доезжать до открытого плана сразу — поправил граммовку в борще, выкатил, и список покупок пересчитался.

**2. Ссылка может указывать в пустоту.**
Блюдо могли убрать из каталога между планированием и походом в магазин. `resolvePlan` молча выбрасывает такие
позиции — `src/entities/plan/lib/shopping-list.ts:53`. Список покупок от этого становится короче, но не врёт.

**3. Отметка о покупке ключуется по продукту, а не по строке списка.**
Строка списка вычисляемая: её текст меняется, как только в план добавили ещё одно блюдо с тем же продуктом.
Отметка «сметана куплена» должна это пережить — поэтому ключ отметки это `product.id`.

**4. Удаление своего продукта убирает его и из плана.**
Каскад лежит в одной транзакции — `src/entities/product/lib/custom-product.ts:63`. Это отличие от
`calories_count`, где удаление блюда не трогает дневник: там запись — свидетельство о съеденном и обязана
остаться, здесь позиция плана — намерение купить то, чего больше не существует.

**5. `id` не переиспользуется.**
Удалил `rice` — этот слаг мёртв навсегда. Иначе состав старого блюда начнёт указывать на другой продукт.
Для «больше не готовлю» есть `archived: true`, и это предпочтительный способ.

## Сборка списка покупок

`buildShoppingList` в `src/entities/plan/lib/shopping-list.ts:111` сводит план в строки:

- состав каждого блюда умножается на `qty` этого блюда;
- продукты, добавленные напрямую, приходят счётчиком штук;
- одинаковые продукты складываются в одну строку, а граммовка и штуки уживаются рядом: `200 г + 1×`;
- группы идут в порядке `categories`, то есть в порядке обхода магазина, а внутри группы — по алфавиту;
- граммы от тысячи переводятся в килограммы, миллилитры — в литры.

Единственный продукт без единицы и в единственном экземпляре печатается без количества: «хлеб», а не «хлеб 1×».

## Экспорт и импорт

Единственная страховка от потери данных: на iOS система может вычистить IndexedDB.

```ts
interface Backup {
	version: 1;
	exportedAt: string;
	plan: PlanItem[];
	checks: Check[];
	customProducts: CustomProduct[];
}
```

Экспорт — скачивание `pantry-YYYY-MM-DD.json`. Импорт — выбор файла, показ содержимого и явный выбор режима:
**заменить всё** или **дополнить**. Файл проверяется целиком до первой записи в базу; посторонние поля из файла
в базу не попадают. Отсутствующий массив `checks` читается как пустой, а не как повреждённый файл, — иначе
копия, снятая до появления отметок, объявлялась бы чужим форматом.
